## 1. 13 号论文到底在干什么

论文题目是：

`World Model-Based Learning for Long-Term Age of Information Minimization in Vehicular Networks`

题目很长，但核心意思其实不复杂。

它研究的是：  
在车联网环境里，系统状态一直在变，车辆在移动，网络条件在波动，决策做错了会影响后面很多步。作者想解决的问题是：

**怎样做长期决策，才能让信息尽量保持“新鲜”。**

这里的 “信息新鲜” 用一个指标表示，叫 `AoI (Age of Information)`。  
你可以先简单理解成：

- 信息越久没更新，AoI 越大；
- AoI 越小，说明系统越及时、越新鲜。

所以这篇文章做的事，就是：

**在一个变化很快的车联网环境里，学习一个策略，让长期 AoI 尽量小。**

---

## 2. 它为什么不用普通 DRL，而要用 world model

这篇论文重要，不是因为它题目里有 “AoI”，而是因为它用了 `world model`。

先用最简单的话讲：

- 普通 `model-free RL / DRL`：边试边学，要靠大量真实交互慢慢撞出来；
- `world model`：先学一个“环境是怎么变化的模型”，再在模型里面做很多想象训练。

你可以把它理解成：

- 普通 DRL：真人下场反复试错；
- world model：先在脑子里或者沙盘里演练很多遍，再决定怎么做。

为什么这在无线/边缘问题里特别有价值？

因为真实试错代价高。

比如在边缘计算里，如果策略乱试，会出现：

- 任务时延变大；
- 用户 QoS 变差；
- 任务超时；
- 队列拥塞；
- 算力和带宽浪费。

所以如果能先学一个“环境替身”，然后在这个替身里训练，价值就很大。

这就是 13 号论文给你的第一层启发：

**world model 很适合这种高动态、试错代价高、目标又是长期优化的问题。**

## 3. 为什么这篇论文对你现在的方向很重要

虽然它做的是 `V2X + AoI`，你现在想做的是 `MEC offloading`，但这两个问题在结构上很像。

它们都具有下面几个特点：

1. 环境一直在变  
   车在动，用户也在动，链路也在变。

2. 当前动作会影响未来很多步  
   现在做一个决定，不只是影响这一时刻，还会影响后面的排队、拥塞和完成时间。

3. 不是一步贪心就能解决  
   有些动作看起来当前好，长期反而差。

4. 普通 DRL 训练成本高  
   要大量交互，样本效率不高。

所以它重要的地方在于：

**它证明了“世界模型做长期控制”这条技术路线在无线/边缘类问题上是站得住的。**

这会让你后面写论文时底气更足，因为 reviewer 不会觉得你是在乱套一个不相干的方法。

## 7. 状态、动作、奖励，应该怎么理解

### 7.1 状态是什么

状态就是“智能体在这一刻能看到什么”。

在你当前环境里，已经有这些信息：

- 当前 step；
- 每个用户的位置；
- 每个用户的速度；
- 每个用户队列长度；
- 当前任务大小；
- 当前任务剩余计算量；
- 当前上行速率；
- MEC 服务器队列长度。

这已经足够作为第一版状态输入。

你可以先把它理解成：

**系统的体检表。**

智能体每一步都看一眼这张体检表，然后决定哪些任务要卸载。

### 7.2 动作是什么

动作就是“这一刻做什么决策”。

你当前环境里的动作定义很简单：

**选出哪些用户在这一时刻把头部任务卸载到 MEC。**

比如：

```python
action = [1, 4, 7]
```

意思就是：本步尝试让 1、4、7 号用户卸载。

这个定义很适合第一版实验，因为它清楚、直接、容易和启发式方法比较。

### 7.3 奖励是什么

奖励就是“系统希望什么样的结果”。

现在环境里的 reward 大致是在鼓励：

- 时延小；
- 丢包少；
- 队列别太长；
- 完成任务越多越好。

这对调试环境是够的。

但如果以后要写论文，reward 需要更像一个正式研究目标，比如：

- 平均完成时延；
- deadline 违约数；
- SLA 违约率；
- 队列积压；
- 卸载代价或能耗。

也就是说：

**现在的 reward 能让你跑实验，但以后要改成更像论文语言的版本。**

## 8. DreamerV3 迁移时，真正要改的是什么

很多人第一次看会误以为：

“迁移 DreamerV3，是不是要把整个算法改一遍？”

其实第一阶段通常不是。

**第一阶段最需要改的，往往是输入输出接口，不是 Dreamer 的核心思想。**

DreamerV3 的核心逻辑你可以先粗略理解成三块：

1. 编码器 `encoder`  
   把观测变成潜在表示；

2. 世界模型 `RSSM / latent dynamics`  
   学系统怎么随着动作演化；

3. actor-critic  
   在想象轨迹里学策略。

对你现在这个 MEC 场景来说，最关键的是第 1 块：

**你的观测不是图像，而是异构数值特征。**

所以最实际的迁移工作是：

- 把每一步观测整理成固定维度向量；
- 设计一个适合数值特征的 encoder；
- 让 Dreamer 可以吃这个状态。

这也是为什么当前项目里 `flatten_observation()` 很重要。  
它相当于已经替你把第一步准备工作做掉了一半。

## 13. 第一版 MEC 问题定义与统一指标

为了保证后续 baseline、DreamerV3 和后续改进方法都在解决同一个问题，当前先将第一版 MEC 问题定义固定如下。

### 13.1 状态

第一版状态先固定为以下量：

- 每个用户：
  - `position`
  - `velocity`
  - `queue_length`
  - `current_task_size`
  - `current_task_remaining_cycles`
  - `uplink_rate`
- 全局状态：
  - `server_queue_length`
  - `max_offloads_per_step`
  - 可选 `step`

这组状态对应 MEC 卸载里最核心的四类信息：用户移动、链路状态、任务负载和 MEC 拥塞。

### 13.2 动作

第一版动作固定为：

- 每个时隙选择哪些用户执行卸载。

当前环境内部仍可使用用户 `id` 列表表示动作；后续对接 DreamerV3 时，统一转成固定长度二值向量表示，每一位对应一个用户是否卸载。

### 13.3 奖励

第一版奖励固定为以下组合：

- 时延惩罚
- 丢弃惩罚
- 队列积压惩罚
- 完成任务奖励

可以写成：

```text
reward =
  - delay_penalty * avg_delay
  - drop_penalty * dropped_tasks
  - queue_penalty * total_queue
  + completion_bonus * completed_tasks
```

当前这版 reward 的作用是先形成一个可训练、可比较的卸载问题；后续如果需要论文化，再进一步改写成更明确的 QoS / SLA 导向目标。

### 13.4 统一评测指标

从当前开始，后续所有 baseline、DreamerV3 和改进方法统一使用以下指标进行比较：

- `avg_reward`
- `completed`
- `dropped`
- `avg_delay`
- `avg_queue`

这样做的目的，是保证后续所有实验结果都在同一套评测标准下可解释、可比较。

## 14. 当前 MEC 环境的 baseline 结果

为了验证当前最小 MEC 环境是否已经具备基本区分度，我在相同环境配置下先跑了 4 条启发式 baseline：

- `random`：随机选择用户卸载
- `local_only`：全部本地处理，不卸载
- `best_uplink`：优先选择当前上行速率最高的用户卸载
- `largest_queue`：优先选择当前队列最长的用户卸载

评测命令为：

```bash
python eval_baselines.py --episodes 20 --seed 7
```

其中：

- `episodes=20` 表示每条策略独立跑 20 个完整回合，再取平均结果
- `seed=7` 表示固定随机种子，保证这轮比较可复现

实验结果如下：

| policy        | avg_reward | completed | dropped | avg_delay | avg_queue |
| ------------- | ---------: | --------: | ------: | --------: | --------: |
| random        |  -1771.620 |     25.05 |  284.90 |     2.318 |    40.523 |
| local_only    |  -1686.124 |     15.35 |  292.45 |     1.272 |    39.219 |
| best_uplink   |  -1766.190 |     30.45 |  275.00 |     2.661 |    40.618 |
| largest_queue |  -1741.590 |     21.85 |  285.90 |     2.024 |    39.994 |

这组结果至少说明了四件事：

1. 当前环境已经具备基本区分度。  
   不同策略在完成任务数、丢弃任务数和平均时延上已经出现明显差异，说明当前 MEC 环境不是“所有策略都差不多”的无效环境。

2. 链路状态对卸载决策确实重要。  
   `best_uplink` 的完成任务数最高、丢弃任务数最少，说明“优先让当前链路好的用户卸载”在当前环境里是有效直觉，这也支持把 `uplink_rate` 纳入状态定义。

3. 只看队列长度有帮助，但不如同时看链路条件。  
   `largest_queue` 整体优于随机，但仍弱于 `best_uplink`，说明未来更合理的策略应该联合考虑“通信条件 + 任务负载”，而不是只盯住单一因素。

4. 当前 reward 设计偏向保守策略。  
   `local_only` 虽然完成任务最少、丢弃任务最多，但 `avg_reward` 反而最好。这说明现有 reward 对平均时延和队列积压更敏感，而对“多完成任务、少丢任务”的鼓励还不够强。换句话说，当前 reward 更偏向“保守不拥塞”，而不是“积极多卸载”。

因此，当前 baseline 的结论不是“哪条启发式已经最优”，而是：

- 这个环境已经可以支撑后续 world model / DreamerV3 的策略比较；
- 当前状态定义里包含的链路信息是有价值的；
- 当前 reward 还需要在后续迁移过程中继续校准；
- DreamerV3 接入后，至少应该重点观察它能否同时超过 `best_uplink` 的完成/丢弃表现，以及避免被 `local_only` 在 reward 上压住。
